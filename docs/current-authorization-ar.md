# حالة المصادقة والصلاحيات الحالية

## القواعد التي تعمل فعليًا

- يستخدم الـAPI مصادقة JWT Bearer موقعة بـHMAC SHA-256.
- يتم التحقق من `Issuer` و`Audience` والتوقيع والانتهاء وClaims الجلسة: `sub` و`sid` و`auth_version`.
- بعد التحقق من JWT يفحص النظام أن المستخدم والجلسة ما زالا صالحين وأن `AuthorizationVersion` يطابق التوكن. نتيجة فحص الجلسة تُحفظ 15 ثانية افتراضيًا وتُبطل محليًا فور Logout أو تغيير كلمة المرور.
- `DefaultPolicy` و`FallbackPolicy` تطلبان مستخدمًا مسجلًا وأن تكون قيمة `password_change_required=false`.
- المستخدم ذو كلمة المرور المؤقتة يستطيع فقط الدخول والتحديث وتغيير كلمة المرور وإدارة جلساته وملفه الشخصي؛ بقية الـEndpoints المحمية تُرفض حتى يغيرها.
- `/health/live` مفتوح. Login وRefresh مفتوحان لأنهما نقطتا دخول المصادقة.
- Swagger مفتوح في `Development` ولا يعرض Bearer security scheme حسب قرار المرحلة، وهو غير مشغّل في `Production`.

## إعدادات الأمان الافتراضية

| الإعداد | القيمة الحالية |
| --- | --- |
| عمر Access Token | 10 دقائق |
| خمول Refresh Token | 7 أيام |
| العمر المطلق لعائلة Refresh | 30 يومًا |
| الحد الأقصى للجلسات النشطة | 10 |
| Cache التحقق من الجلسة | 15 ثانية |
| Cache الصلاحيات | 60 ثانية كحد أقصى، ويقصر تلقائيًا عند بداية أو نهاية فترة منح |
| انحراف ساعة JWT المسموح | 30 ثانية |
| الحد الأدنى لكلمة المرور | 12 محرفًا |
| تعقيد كلمة المرور | حرف كبير وصغير ورقم ورمز |
| قفل الحساب | بعد 5 محاولات فاشلة لمدة 15 دقيقة |
| تأكيد البريد/الحساب | مطلوب قبل Login |

الحالات المسموح لها بالدخول هي `Active` و`PendingTemporaryPassword`. حالات `Locked` و`Suspended` و`Archived` مرفوضة.

## حساب التطوير الافتراضي

عند تشغيل الـAPI في بيئة `Development` مع `DevelopmentIdentity:Enabled=true` ينشأ الحساب مرة واحدة فقط بعد تطبيق ترحيلات Identity:

| الحقل | القيمة |
| --- | --- |
| Username | `Omar` |
| Temporary Password | `P@ssword1234` |
| Role | `SYSTEM_ADMIN` |
| Direct permissions | كل الصلاحيات الـ55 مع جميع نطاقات العميل والسكن |
| RequiresPasswordChange | `true` |
| IsDevelopmentOnly | `true` |

لا يعيد الـSeeder ضبط كلمة المرور إذا كان الحساب موجودًا. ويكمل أي Grant تطويري ناقص دون حذف أو تغيير السجلات القديمة. الحساب موسوم داخل قاعدة البيانات بأنه خاص بالتطوير، وLogin وفحص الجلسة يرفضانه عندما يعمل التطبيق في `Production` حتى لو أشارت البيئتان إلى قاعدة واحدة بالخطأ. لا تستخدم كلمة المرور هذه لأي حساب حقيقي.

لا يوجد Username أو Password افتراضي للإنتاج. ينشأ أول مسؤول إنتاج بواسطة أداة Bootstrap ذات إدخال كلمة مرور مخفي والموضحة في دليل تجهيز الإنتاج.

## الأدوار الثلاثة المحمية

| الدور | الغرض | الصلاحيات الأساسية |
| --- | --- | --- |
| `SYSTEM_ADMIN` | إدارة أمن النظام، وليس امتلاك كل بيانات الأعمال تلقائيًا | 13 صلاحية لإدارة المستخدمين والأدوار والصلاحيات والتدقيق ووصول الدعم والمدن وقراءة التقارير |
| `MANAGER` | نقطة بداية تشغيلية محدودة | 8 صلاحيات قراءة أساسية؛ صلاحيات المنصات والسكن لا تعمل دون نطاق مناسب |
| `USER` | مستخدم عادي | الملف الشخصي والجلسات فقط؛ لا توجد صلاحية أعمال أساسية |

الأدوار محمية من الأرشفة أو التعديل، ومنحها الأساسية ثابتة. الاختلافات بين الموظفين تُنفذ بمنح أو منع مباشر وبنطاقات، وليس بإنشاء عدد كبير من الأدوار. القائمة الكاملة موجودة في [كتالوج الصلاحيات](authorization-permission-catalog-ar.md).

## محرك الصلاحيات

- أي Permission غير معروفة أو غير مزروعة أو Deprecated تُرفض: `default deny`.
- يجب أن يكون الدور والتكليف وفترة المنح نشطين في وقت الطلب.
- `Deny` مباشر قابل للتطبيق يتغلب على Grant مباشر وعلى أي Grant آتٍ من دور.
- `Deny` لصلاحية Scoped من دون نطاق محدد يُعامل كمنع شامل لتجنب تسريب الصلاحية بسبب إعداد ناقص.
- صلاحيات السكن تحتاج `IsAllHousingScope` أو `AccessScopeType.Housing` مطابقًا.
- صلاحيات العميل تحتاج `IsAllClientScope` أو نطاق منصة/عقد مطابقًا. يمكن لنطاق منصة أن يشمل عقودها المستقبلية فقط عند تفعيل `IncludesFuturePlatformContracts`.
- الـAuthorization Handler الديناميكي يستخدم Policy باسم `permission:<key>`. ويستخدم الـController مستقبلًا `[RequirePermission(PermissionKeys.Workforce.EmployeesRead)]` بدل فحص اسم الدور.
- عند Permission ذات نطاق، يسمح الـAttribute العام فقط لمن يحمل All Scope. الـEndpoint الذي يستهدف سكنًا أو منصة أو عقدًا محددًا يجب أن يستدعي `IPermissionChecker` مع `PermissionScope` للهدف؛ لا يكفي فحص المفتاح خارج سياق المورد.
- `AuthorizationVersion` جزء من مفتاح Cache ومن الجلسة؛ أي تغيير تفويض يجب أن يزيده ويبطل جلسات/Cache المستخدم عبر Service إدارة الصلاحيات عند تنفيذها.

## DeviceLabel في Login

`DeviceLabel` اختياري وليس شرطًا للدخول. هو اسم يختاره العميل لتسهيل معرفة الجلسة مثل `Omar Laptop` أو `Office PC`:

```json
{
  "login": "Omar",
  "password": "P@ssword1234",
  "deviceLabel": "Omar Laptop"
}
```

القيمة تُقص وتُنظف ويُحفظ منها 200 محرف كحد أقصى. إذا كانت فارغة تُحفظ `null`. لا يعتمد عليها النظام لإثبات هوية الجهاز؛ لكل جلسة Refresh Token مستقل، بينما يُحفظ User-Agent كبصمة SHA-256 منفصلة.

## تدوير Refresh Token

- لا يُخزن Refresh Token كنص؛ تحفظ بصمة SHA-256 فقط.
- Login ينشئ Session وعائلة Refresh جديدة.
- Refresh ناجح يغلق Session السابقة وينشئ Session جديدة داخل العائلة نفسها.
- إعادة استخدام Token قديم تلغي جميع الجلسات النشطة في عائلته.
- تغيير كلمة المرور يلغي كل الجلسات، يزيد `AuthorizationVersion`، ثم يعيد Access/Refresh جديدين.
- لا توجد عمليات حذف للجلسات؛ الإلغاء يحفظ الوقت والسبب والمستخدم المنفذ.

## Endpoints الحالية

| Method | Route | الحماية | الوظيفة |
| --- | --- | --- | --- |
| POST | `/api/auth/login` | Anonymous | دخول باسم المستخدم أو البريد وكلمة المرور؛ `DeviceLabel` اختياري. |
| POST | `/api/auth/refresh` | Anonymous | تدوير Refresh Token وإصدار Token جديد. |
| POST | `/api/auth/logout` | JWT، مسموح أثناء تغيير كلمة المرور | إلغاء الجلسة الحالية. |
| POST | `/api/auth/logout-all` | JWT، مسموح أثناء تغيير كلمة المرور | إلغاء كل الجلسات وزيادة إصدار الصلاحيات. |
| POST | `/api/auth/change-password` | JWT، مسموح أثناء تغيير كلمة المرور | تغيير كلمة المرور وإصدار جلسة جديدة. |
| GET | `/api/auth/sessions` | JWT، مسموح أثناء تغيير كلمة المرور | آخر 50 جلسة للمستخدم. |
| POST | `/api/auth/sessions/{id}/revoke` | JWT، مسموح أثناء تغيير كلمة المرور | إلغاء جلسة يملكها المستخدم. |
| GET | `/api/user-profile/me` | JWT، مسموح أثناء تغيير كلمة المرور | الحساب وبيانات الموظف والرايدر والتكليف الحالي. |
| PATCH | `/api/user-profile/me/preferences` | JWT، مسموح أثناء تغيير كلمة المرور | تعديل اللغة والثيم وكثافة العرض. |
| GET | `/api/user-profile/me/authorization` | JWT، مسموح أثناء تغيير كلمة المرور | الأدوار والمنح والمنع والنطاقات والصلاحيات الفعالة. |

## ما لا يزال مطلوبًا قبل الإنتاج الكامل

- Services وControllers لإدارة المستخدمين وتكليف الأدوار والمنح المباشر والنطاقات؛ مفاتيح حمايتها موجودة لكن واجهات إدارتها لم تنفذ بعد.
- وضع `[RequirePermission]` على كل Endpoint أعمال عند إنشاء خدمات الموظفين والرايدرز والوثائق والتشغيل.
- في النشر متعدد النسخ يجب نقل Cache الجلسات والصلاحيات والإبطال إلى Distributed Cache مثل Redis، أو اعتماد آلية invalidation مشتركة.
- إضافة اختبارات تكامل واختبارات مصفوفة الصلاحيات قبل التعامل مع بيانات حقيقية؛ تم تأجيل الاختبارات آليًا في هذه المرحلة بقرار المشروع فقط.
