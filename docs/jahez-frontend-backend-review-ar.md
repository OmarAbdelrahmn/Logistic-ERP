# مراجعة جاهز بين الـFrontend والـBackend

تاريخ المراجعة: **10 أكتوبر 2026 — توقيت الرياض**.

هذا الملف يوثق التنفيذ الموجود في ملفات خدمة جاهز المحلية، لمراجعة شاشات الفرونت وطلبات الشبكة مع مبرمج الواجهة. لا يمثل اقتراحًا تم تنفيذه، ولا تأكيدًا بأن النسخة المنشورة تطابق هذه الملفات. لم تتغير ملفات الكود أو قاعدة البيانات أثناء إعداد هذه المراجعة، ولم تُرسل عمليات مالية حقيقية.

**النتيجة الرئيسية:** الـBackend يدعم أربعة أنواع من طلبات الموافقة فقط: إعفاء رسوم حساب، تبديل مجاني، تحويل العمولة إلى 15% لفترة محددة، وتصفير/إغلاق الحساب مع إبقاء مسؤولية الدين على المندوب السابق. **لا يوجد نوع طلب موافقة لتخفيض مبلغ عمولة مستحق، أو تخفيض مديونية جاهز، أو تغيير العمولة اليومية من 15 إلى مبلغ آخر.** توجد تسوية مالية مباشرة بصلاحية خاصة، وهي عملية مختلفة عن طلب الموافقة.

لم تتم مراجعة كود الفرونت أو طلباته الفعلية في هذه المراجعة. المتاح من الواجهة صورة شاشة التحصيل التي عرضها صاحب النظام، ووصفه لوجود طلب تخفيض. لذلك مخالفة شاشة التخفيض للعقد الحالي احتمال يحتاج فحص طلب الشبكة، وليست نتيجة مثبتة على الفرونت.

## 1. جدول الدعم الحالي — ابدأ به عند مراجعة الواجهة

| الوظيفة في الفرونت | الدعم الحالي | العملية الفعلية |
|---|---|---|
| استلام حساب جاهز | مدعوم | إنشاء فترة استخدام ورسوم 200 ريال |
| تسجيل سداد كامل أو جزئي | مدعوم | قبض موزع على الرسوم والمديونية والعمولة |
| حساب العمولة اليومية تلقائيًا | مدعوم | 15 ريال لكل يوم مستحق لكل حساب |
| إعفاء من رسوم الحساب | طلب موافقة مدعوم | `kind: 1`؛ لا يخص العمولة أو دين جاهز |
| تبديل الحساب بدون رسوم استلام جديدة | طلب موافقة مدعوم | `kind: 2`؛ الالتزامات القديمة تبقى |
| التحويل إلى عمولة 15% | طلب موافقة مدعوم | `kind: 3`؛ فترة من/إلى، وبيانات أرباح منفصلة |
| تصفير الحساب | طلب موافقة مدعوم | `kind: 4`؛ إغلاق الاستخدام وإتاحة الحساب، لا محو الدين |
| طلب تخفيض مبلغ العمولة القديمة | غير موجود كنوع طلب موافقة | لا يوجد `kind` مستقل لهذه الوظيفة |
| طلب تخفيض مديونية جاهز | غير موجود كنوع طلب موافقة | لا يوجد `kind` مستقل لهذه الوظيفة |
| تغيير اليومية إلى 10 ريال مثلًا | غير مدعوم في العقد الحالي | اليومية ثابتة 15 |
| اختيار نسبة 10% أو 20% | غير مدعوم في طلب النسبة الحالي | النسبة ثابتة 15%؛ لا يوجد حقل `rate` في الطلب |
| تخفيض رصيد بقيد مالي موثق | مدعوم كعملية مباشرة | `POST /adjustments`؛ لا ينشئ طلب موافقة |
| تسجيل تحويل أموال آلي إلى جاهز | غير موجود في الوحدة | التحصيل والصندوق داخليان |
| إرفاق إيصال أو تحديد طريقة الدفع في طلب التصفية | غير موجود في عقد التصفية | لا توجد حقول مرفق/طريقة دفع/رقم تحويل في `PaymentRequest` |

## 2. المصطلحات والمعرفات

| المصطلح | المعنى والاستخدام |
|---|---|
| `accountId` | معرف حساب المنصة داخل النظام، من نوع UUID |
| `externalAccountId` | رقم الحساب في جاهز؛ يطابق `Driver ID` في ملفات التقارير |
| `riderProfileId` | المندوب الفعلي الذي يستخدم الحساب |
| صاحب الحساب الرسمي | مالك الحساب المسجل؛ قد يختلف عن المندوب الفعلي |
| `assignmentId` | معرف إسناد الحساب الموجود في نظام المنصات |
| `handoverId` | معرف فترة استلام جاهز؛ معظم العمليات المالية ترتبط به |
| `batchId` | معرف دفعة استيراد التقارير |
| `rowId` | معرف صف داخل معاينة الاستيراد |
| `requestId` | معرف طلب موافقة؛ يستخدم في القرار والإلغاء |
| معرف تسليم الصندوق | معرف مختلف عن `handoverId` الخاص باستلام الحساب |

الحساب الواحد قد يمر على عدة مندوبين. الالتزام يتبع فترة المستخدم الفعلي وقت الحركة، ولا ينتقل تلقائيًا إلى صاحب الحساب أو مستخدمه الجديد. تغيير المستخدم لا يمحو تاريخ المستخدم السابق.

كفيل الحساب هو `sponsorId` في حساب المنصة. لا يوجد كفيل داشبورد مستقل في العقد الحالي، وكفيل الموظف بالموارد البشرية علاقة أخرى.

## 3. قواعد مشتركة لجميع مسارات جاهز

- المسار الأساسي: `/api/jahez`.
- المصادقة عبر `Authorization: Bearer <access_token>`.
- كل POST في الوحدة يحتاج `Idempotency-Key` غير فارغ، بحد 150 حرفًا.
- إعادة المحاولة للعملية نفسها وبنفس المستخدم والمفتاح والجسم تعيد نتيجة العملية الأصلية. تغيير الجسم بالمفتاح نفسه ينتج تعارضًا 409. الصلاحية الحالية تُراجع عند إعادة المحاولة أيضًا.
- JSON بصيغة `camelCase`. أنواع جاهز الرقمية تُرسل كأرقام، لا أسماء نصية.
- التواريخ اليومية `yyyy-MM-dd`. اللحظات الزمنية ISO 8601 مع المنطقة الزمنية، مثل `2026-10-10T09:00:00+03:00`؛ تحفظ UTC.
- الأيام المالية والتأخر محسوبة بتوقيت الرياض.
- السبب مطلوب في أوامر العمل التي تستقبله، بحد 2000 حرف، ولا يقبل فراغًا فقط.
- العملة ريال سعودي. مبالغ القبض بدقة منزلتين عشريتين؛ بيانات المصدر والقيود قد تكون بدقة 6 منازل.
- القوائم تعيد `{ items, page, pageSize }`، الافتراضي صفحة 1 وحجم 50، الحجم بين 1 و100، ولا يوجد `totalCount` في عقد صفحة جاهز.
- الرد الناجح JSON يأتي مباشرة مع HTTP 200، دون غلاف `data`. تنزيل ملف الاستيراد يعيد XLSX.
- لا تستخدم زمن المتصفح لحساب العمولة أو تجاوز تحقق التواريخ؛ مصدر الحساب النهائي هو الـBackend.

مثال رؤوس طلب JSON:

~~~http
Authorization: Bearer <access_token>
Content-Type: application/json
Idempotency-Key: <unique-key-for-this-command>
~~~

## 5. إنشاء الحساب واستلامه

حساب المنصة ينشأ من API الحسابات العام، ثم يسلم للمندوب عبر جاهز. لا تستخدم مسار الإسناد العام أو الإغلاق العام لحساب جاهز، لأنه يتعارض مع قواعد الوحدة المالية.

قبل الاستلام يجب أن يكون الحساب من منصة جاهز، متاحًا `Available`، وبنظام الدفع حسب الطلب `PayPerOrder`، وله كفيل صالح. المندوب موظف نشط، ولا توجد فترة استخدام متداخلة. حد الإسنادات النشطة الذي يفحصه هذا المسار للمندوب هو حسابان ضمن الخانتين الحاليتين.

~~~json
{
  "accountId": "11111111-1111-1111-1111-111111111111",
  "riderProfileId": "22222222-2222-2222-2222-222222222222",
  "effectiveAtUtc": "2026-10-09T09:00:00+03:00",
  "reason": "استلام حساب جاهز",
  "initialFeePayment": 80,
  "feeApprovalRequestId": null
}
~~~

- `effectiveAtUtc` لا يكون في المستقبل.
- رسوم الاستلام الجديد 200 ريال. دفعة أولى اختيارية من 0 إلى 200.
- المثال يسجل قبض 80 في صندوق الرسوم، ويتبقى 120.
- الدفعة الأولى ليست تصفية ولا تعيد نقطة تذكير التصفية.
- يوم الاستلام معفى من اليومية؛ البداية اليوم التالي.
- `feeApprovalRequestId` موجود في العقد لكنه يجب أن يكون null في الاستلام العادي؛ الإعفاء يتم بطلب لاحق أو بالتبديل المجاني المعتمد.
- احفظ `id` من الرد؛ هذا هو `handoverId` المستخدم لاحقًا.
- لا تغير رقم الحساب الخارجي أو منصته بعد وجود تاريخ مالي لجاهز.

### تهيئة حساب قديم

`POST /legacy-adoptions` يحول إسنادًا قائمًا إلى تاريخ مالي جاهز دون اختراع رسوم 200 أو عمولات تاريخية:

~~~json
{
  "assignmentId": "44444444-4444-4444-4444-444444444444",
  "financialStartOn": "2026-10-08",
  "openingDebt": 42,
  "openingFees": 0,
  "openingCommission": 30,
  "reason": "تهيئة إسناد قديم بأرصدة افتتاحية موثقة"
}
~~~

الإسناد يجب أن يكون غير مغلق ولم تتم تهيئته مسبقًا. البداية المالية داخل فترة الإسناد وحتى اليوم. الرسوم والعمولة الافتتاحية غير سالبتين؛ الدين الافتتاحي يقبل السالب كرصد دائن. القيم بحد مليار ودقة 6 منازل. اليومية تبدأ من `financialStartOn` نفسه للحساب القديم. لا يوجد قبض أو صندوق من الأرصدة الافتتاحية. تجنب استيراد حركات سبق تضمينها في الافتتاحي، وحدد نقطة بداية مالية واضحة.

## 6. معاينة الرصيد

~~~http
GET /api/jahez/handovers/{handoverId}/balance?through=2026-10-10
~~~

| حقل الرد | التفسير |
|---|---|
| `fees` | الرسوم المتبقية بعد الدفعات والإعفاءات والتسويات |
| `platformDebt` | مديونية جاهز الحالية مع قطع حركات المصدر حتى نهاية التاريخ؛ السالب رصيد دائن |
| `postedCommission` | رصيد العمولة المثبتة سابقًا بعد المدفوع والتسويات |
| `unpostedCommission` | العمولة الجديدة المحسوبة وغير المثبتة بعد |
| `totalReceivable` | مجموع البنود: `fees + platformDebt + postedCommission + unpostedCommission` |
| `commissionComplete` | هل بيانات حساب النسبة مكتملة؟ |
| `problems` | أسباب نقص بيانات العمولة |
| `throughDate` | تاريخ المعاينة المطلوب |
| `latestTransactionAtUtc` | آخر حركة جاهز مستوردة نشطة؛ null إذا لا توجد حركات |
| `reminderAnchorAtUtc` | تاريخ الاستلام أو آخر قبض محسوب كتصفية |
| `daysSinceSettlementPayment` | أيام الرياض المنقضية من نقطة التذكير |
| `isOverdue` | هل الحساب متأخر وفق قواعد المتابعة؟ |
| `debtTransferred` | هل الإغلاق سجل نقل مسؤولية المتابعة؟ لا يعني محو الرصيد |

لعرض «العمولة المستحقة» في واجهة الدفع استخدم `postedCommission + unpostedCommission`. حساب العميل المحلي لا يحل محل المصدر النهائي.

المعاينة لا تكتب قبضًا ولا تثبت العمولة في الدفتر. اختيار التاريخ لا يسبق الاستلام أو آخر عمولة مثبتة أو آخر فترة تصفية، ولا يتجاوز اليوم. هذا رصيد حالي، وليس لقطة تاريخية قبل دفعات لاحقة؛ التاريخ يقطع حركات المصدر بينما الدفعات والتسويات الحالية تدخل في الرصيد. للتاريخ استخدم الدفتر وسجل التصفية.

لا تعامل `latestTransactionAtUtc` كضمان اكتمال كل تقارير جاهز؛ هو وقت آخر حركة موجودة فقط.

## 7. حساب العمولة اليومية والنسبة

### اليومية

- 15 ريال يوميًا لكل حساب مستقلًا.
- الاستلام الجديد: من اليوم التالي لتاريخ الاستلام بالرياض.
- الحساب القديم المهيأ: من البداية المالية الصريحة.
- لا يعتمد الاستحقاق على عدد الطلبات أو وجودها.
- يوم الإغلاق محسوب إذا كان بعد يوم الاستلام.
- تثبيت أيام في تصفية لا يجعلها تُحسب مرة أخرى؛ الحساب التالي يبدأ بعد آخر يوم مثبت.
- التصفية لا توقف استخدام الحساب أو عمولة الأيام التالية.

### النسبة

15% خلال فترة معتمدة، بدل اليومية لنفس الأيام. خارج الفترة يرجع الحساب اليومي.

~~~text
أساس الأرباح =
  totalDeliveryPrice
  - totalPenalties
  - totalCashAmount
  - totalDriverDebit
  - totalServiceDeduction
  + totalDriverCredit
  + totalBonuses
  + totalTips
  + totalFreeOrders

العمولة = تقريب(max(0, أساس الأرباح للفترة المحسوبة) × 0.15، هللتين)
~~~

النسبة ليست بالضرورة أقل من اليومية. إذا كانت الفترة 10 أيام وأساسها 500، النسبة 75 بدل اليومية 150؛ وإذا أساسها 2000 تصبح النسبة 300.

## 8. التحصيل والتصفية — حقول الشاشة المعروضة

~~~json
{
  "handoverId": "33333333-3333-3333-3333-333333333333",
  "throughDate": "2026-10-10",
  "feePayment": 0,
  "debtPayment": 42,
  "commissionPayment": 10,
  "countsAsSettlement": true,
  "reason": "سداد مديونية جاهز ودفعة جزئية من العمولة"
}
~~~

| عنصر الشاشة | حقل الـAPI/المصدر | الاستخدام |
|---|---|---|
| اختر حساب التسليم | `handoverId` | فترة الاستخدام المسؤولة عن الالتزام |
| حتى تاريخ | `throughDate` | آخر يوم مطلوب تثبيت العمولة حتى نهايته |
| رسوم مستحقة | `balance.fees` | عرض، لا مبلغ قبض |
| مديونية جاهز | `balance.platformDebt` | عرض، لا مبلغ قبض |
| العمولة | مجموع `postedCommission + unpostedCommission` | عرض تلقائي |
| تحصيل رسوم الحساب | `feePayment` | المقبوض فعلًا للرسوم |
| تحصيل مديونية جاهز | `debtPayment` | المقبوض فعلًا للمديونية |
| تحصيل عمولة التشغيل | `commissionPayment` | المقبوض فعلًا للعمولة |
| تحسب كتصفية رسمية | `countsAsSettlement` | تثبيت العمولة وتحديث آخر تاريخ تصفية |
| سبب التحصيل | `reason` | وصف مطلوب |

### قواعد التصفية

- المبالغ أرقام غير سالبة، بدقة هللتين، كل منها بحد مليار، ومجموعها أكبر من صفر.
- لا تدفع أكثر من الرصيد الموجب لكل بند، حتى لو مجموع الدفعة أقل من الإجمالي.
- `countsAsSettlement: false` مسموح للرسوم فقط: `debtPayment = commissionPayment = 0`.
- أي قبض مديونية أو عمولة يتطلب true. وصف الاختيار بأنه «اختياري» دون هذا الشرط في الفرونت مضلل ويحتاج مراجعة.
- `true` يثبت العمولة حتى `throughDate`، حتى لو `commissionPayment` صفر، طالما يوجد قبض في بند آخر.
- `true` يحدث آخر تصفية إلى وقت تسجيل القبض الحالي، وليس إلى `throughDate`. ويعيد عد التذكير حتى مع دفعة جزئية أو دفعة رسوم فقط محسوبة كتصفية.
- المديونية والعمولة المقبوضتان تدخلان قسم التصفيات، والرسوم قسم الرسوم.
- لا يحدث صرف آلي إلى جاهز.
- العميل يحدد توزيع المبلغ صراحة. لا يوجد حقل «مبلغ إجمالي» يجعل الخدمة توزعه تلقائيًا.
- عند عدم اكتمال بيانات النسبة، تثبيت التصفية يُرفض. اعرض `problems` قبل محاولة التأكيد.
- لا يوجد قبول لدفعة صفر بغرض تحديث تاريخ التصفية فقط.

### مثال مطابق للأرقام المعروضة

قبل الدفع: رسوم 0، دين 42، عمولة 30. الطلب أعلاه يقبض 52: الدين 42 والعمولة 10. بعده: رسوم 0، دين 0، عمولة 20، والصندوق يزيد 52 في قسم التصفيات.

إذا لم يدفع الدين وأردت قبض 10 عمولة فقط، `debtPayment` يجب أن يكون 0. اليومية التالية تضيف 15 إذا الحساب ما زال نشطًا وخارج فترة نسبة؛ فيصبح مستحق العمولة 35: المتبقي 20 + اليومية الجديدة 15.

اقتراح واجهة للمراجعة: زر «سداد كامل» يمكنه تعبئة مبالغ التحصيل من معاينة الرصيد، مع بقاء إمكانية السداد الجزئي. هذا اقتراح UX وليس سلوكًا جديدًا نُفذ في الكود.

رد التصفية يحوي `id, handoverId, throughDate, recordedAtUtc, collectedByUserId, feePayment, debtPayment, commissionPayment, countsAsSettlement, reason`، وبيانات العرض والتدقيق. الرد ليس كشف الرصيد المتبقي؛ أعد GET للرصيد والصندوق وسجل الدفعات بعد النجاح.

## 9. طلبات الموافقة الأربعة

ترسل جميعها إلى `POST /requests`. الطلب يتسجل معلقًا ولا يطبق الأثر المالي بمجرد إرساله.

### النوع 1: إعفاء رسوم حساب

~~~json
{
  "handoverId": "33333333-3333-3333-3333-333333333333",
  "kind": 1,
  "waiverAmount": 50,
  "reason": "طلب إعفاء جزئي من رسوم استلام الحساب"
}
~~~

`waiverAmount` موجب، بحد 200، وبدقة هللتين. عند الاعتماد لا يتجاوز الرسوم غير المدفوعة، ولا يزيد مجموع الإعفاءات عن أصل الرسوم. لا يعيد فلوسًا سبق قبضها.

**هذا النوع يخص رسوم الحساب فقط.** إرسال مبلغ تخفيض عمولة في `waiverAmount` مع `kind: 1` لا يجعله إعفاء عمولة؛ الاعتماد يؤثر على بند الرسوم.

### النوع 2: تبديل مجاني

~~~json
{
  "handoverId": "33333333-3333-3333-3333-333333333333",
  "kind": 2,
  "targetAccountId": "55555555-5555-5555-5555-555555555555",
  "effectiveAtUtc": "2026-10-10T09:00:00+03:00",
  "reason": "طلب تبديل الحساب بسبب ضعف الطلبات"
}
~~~

الحساب البديل مختلف ومتاح وقت الاعتماد، والفترة الحالية غير مغلقة. اللحظة بين الاستلام والوقت الحالي.

عند الموافقة يغلق القديم ويثبت عمولته وينشئ استلامًا جديدًا للمندوب نفسه مع إعفاء 200 رسوم الاستلام الجديد. رسوم الحساب القديم وديونه وعمولاته المتبقية تبقى على الفترة القديمة، وتُعلّم متابعة المسؤولية القديمة بالنقل. يوم استلام الجديد معفى؛ القديم قد يستحق عمولة يوم الإغلاق. لا تفترض أن التبديل يمحو رصيد القديم.

إذا أصبح البديل مشغولًا قبل القرار، العملية تُرفض دون تطبيق تبديل جزئي.

### النوع 3: تحويل العمولة إلى 15%

~~~json
{
  "handoverId": "33333333-3333-3333-3333-333333333333",
  "kind": 3,
  "fromDate": "2026-10-11",
  "toDate": "2026-10-20",
  "reason": "طلب عمولة نسبة لفترة ضعف الطلبات"
}
~~~

`fromDate` و`toDate` مطلوبان؛ البداية من بداية استحقاق العمولة أو بعدها، والنهاية لا تسبق البداية. فرق اليومين لا يتجاوز 731، أي فترة شاملة حتى 732 يومًا. لا تتجاوز نهاية الاستخدام إذا مغلق.

عند الاعتماد:

- البداية يجب أن تكون بعد `commissionPostedThrough` إن وجد؛ لا تشمل أيام عمولة مثبتة.
- لا تتداخل مع أي سياسة نسبة معتمدة أخرى.
- تُنشأ سياسة بنسبة ثابتة 0.15؛ لا توجد قيمة نسبة يرسلها الفرونت.
- لا يُقبل «مبلغ تخفيض» في هذا الطلب باعتباره أساسًا لحساب العمولة.
- يتطلب الحساب المالي لاحقًا كشوف أرباح تغطي أيام النسبة المراد تصفيتها.
- النسبة تطبق خلال الفترة فقط، ثم يرجع 15 ريال يوميًا.
- الالتزامات القديمة لا تمحى ولا تتحول تلقائيًا إلى نسبة.

### النوع 4: تصفير/إغلاق الحساب ونقل مسؤولية متابعة الدين

~~~json
{
  "handoverId": "33333333-3333-3333-3333-333333333333",
  "kind": 4,
  "effectiveAtUtc": "2026-10-10T09:00:00+03:00",
  "externalResetReference": "مرجع الإجراء اليدوي إن وجد",
  "reason": "إنهاء استخدام المندوب وإتاحة الحساب"
}
~~~

يتطلب فترة استخدام حالية ولحظة صالحة، واعتماد مستخدم آخر بصلاحية `jahez.resets.approve`. المرجع الخارجي اختياري بحد 500 حرف.

الاعتماد يغلق الاستخدام ويثبت العمولة ويجعل الحساب متاحًا لمندوب جديد. الدين يبقى على المندوب السابق، وقيد نقل المسؤولية قيمته صفر؛ لا يكرر أصل الدين ولا يقبض مالًا. المرجع يوثق إجراءً خارجيًا يدويًا، ولا ينفذ تصفيرًا آليًا في منصة جاهز.

الحركة المتأخرة التي وقع وقتها أثناء الاستخدام القديم تُربط بالمندوب القديم عند استيرادها.

## 10. القرار والإلغاء وحالات الطلب

~~~http
POST /api/jahez/requests/{requestId}/decision
~~~

~~~json
{
  "approve": true,
  "reason": "تم التحقق واعتماد الطلب"
}
~~~

للرفض `approve: false` مع سبب. مقدم الطلب لا يعتمد ولا يرفض طلبه بنفسه. يجب أن يكون معلقًا؛ القرار النهائي لا يعاد تطبيقه كموافقة جديدة. تتحقق صلاحية الاعتماد حسب نوع الطلب، إضافة إلى `jahez.read`.

الإلغاء عبر `POST /requests/{id}/cancel`، بجسم `{ "reason": "لم يعد الطلب مطلوبًا" }`، بواسطة مقدم الطلب فقط وهو معلق.

| `status` | الحالة |
|---|---|
| 1 | معلق |
| 2 | معتمد |
| 3 | مرفوض |
| 4 | ملغى |

POST الإنشاء والتفاصيل والقرار يعيدون `{ request, decisions }`. قائمة GET تعيد الطلبات داخل `items`. القرار ينشئ إشعارًا داخليًا للمقدم؛ ليس رسالة خارج النظام أو طلبًا إلى شركة جاهز.

## 11. تخفيض المبلغ: كيف تراجع ما فعله الفرونت؟

اطلب فتح Network عند ضغط زر «طلب تخفيض» وسجل الطريقة والمسار والجسم والرد. المقارنة تكون وفق التالي:

| ما يرسله الفرونت | تفسير الـBackend الحالي | نتيجة المراجعة |
|---|---|---|
| `POST /requests` مع `kind: 1, waiverAmount` | إعفاء رسوم الحساب | صحيح للرسوم؛ غير صحيح إذا الشاشة تسميه إعفاء عمولة/دين |
| `POST /requests` مع `kind: 3, fromDate, toDate` | تحويل إلى 15% لفترة | صحيح للتحويل؛ لا يمثل تخفيض مبلغ محدد |
| `POST /requests` مع `kind: 5` أو قيمة أخرى | نوع غير معرف | الطلب مرفوض |
| `POST /requests` مع `kind: 3` ومبلغ تخفيض إضافي | عقد نوع 3 لا يستخدم مبلغ التخفيض | لا يوجد أثر تخفيض مبلغ ضمن الخدمة؛ لا تعتبر قبول الطلب دليلًا على تنفيذ الحقل الإضافي |
| `POST /adjustments` مع `bucket: 3, amount: -10` | تخفيض رصيد العمولة مباشرة بقيد تسوية | مدعوم كعملية مباشرة؛ لا توجد مرحلة اعتماد لهذا القيد |
| `POST /adjustments` مع `bucket: 2, amount: -10` | تخفيض مديونية جاهز مباشرة | ليس طلب موافقة |
| تقليل `commissionPayment` في `POST /settlements` | قبض أقل، والباقي يظل مستحقًا | سداد جزئي، وليس إعفاءً |
| تعديل رقم العمولة في حالة الفرونت فقط | لا توجد كتابة مالية في الـBackend | تغيير العرض وحده لا يغير الالتزام |

وجود حقول إضافية في JSON لا يضيف دعمًا تجاريًا لها؛ طريقة قبولها/رفضها عند الربط تعتمد على إعدادات JSON، والخدمة تستخدم حقول العقد المعروفة فقط. افحص الأثر المالي الفعلي في الرصيد والدفتر.

### التسوية المباشرة الموجودة

~~~http
POST /api/jahez/adjustments
~~~

~~~json
{
  "handoverId": "33333333-3333-3333-3333-333333333333",
  "bucket": 3,
  "amount": -10,
  "reason": "تسوية موثقة بتخفيض رصيد العمولة",
  "reversesEntryId": null
}
~~~

الموجب يزيد الالتزام، والسالب يخفضه. `bucket: 1` للرسوم، 2 للمديونية، 3 للعمولة. المبلغ غير صفر، بحد مليار ودقة 6 منازل. التنفيذ يتطلب `jahez.adjustments.create` ويؤثر فورًا في الدفتر. لا يكتب قبضًا أو صندوقًا أو آخر تصفية، ولا يغير اليومية أو النسبة، ولا ينشئ سجل طلب موافقة/قرار.

لا يوجد تحقق عام في `AdjustAsync` يربط التخفيض العادي بقيمة الرصيد المتبقي؛ لا تقدم هذه العملية في الفرونت كإعفاء مضبوط بسقف المستحق أو كموافقة مدير دون وجود هذا المسار فعلًا. هذه ملاحظة عن التنفيذ الحالي وليست تعديلًا أو توصية باستعماله بدل وظيفة الموافقات المطلوبة.

`reversesEntryId` اختياري لعكس استحقاق سابق: نفس فترة الاستلام والبند، والمبلغ المعاكس تمامًا، ولم يعكس سابقًا. لا يسمح بعكس قيد قبض نقدي أو نقل مسؤولية بهذه الواجهة.

إذا المطلوب التجاري هو «الموظف يطلب تخفيض 10 من عمولة مستحقة والمدير يوافق»، فهذه **وظيفة تحتاج عقدًا وتنفيذًا إضافيين**. يلزم تحديد البند، مبلغ التخفيض، الصلاحيات، مرحلة القرار، سقف التخفيض، وأثره في الدفتر. لا تعتبر التسوية المباشرة تنفيذًا لهذا المسار.

## 12. إدخال أرباح فترة النسبة

`POST /earnings` بعد اعتماد سياسة تغطي الفترة:

~~~json
{
  "handoverId": "33333333-3333-3333-3333-333333333333",
  "fromDate": "2026-10-02",
  "toDate": "2026-10-06",
  "totalDeliveryPrice": 1000,
  "totalPenalties": 20,
  "totalCashAmount": 100,
  "totalDriverDebit": 10,
  "totalServiceDeduction": 5,
  "totalDriverCredit": 50,
  "totalBonuses": 30,
  "totalTips": 10,
  "totalFreeOrders": 5,
  "reason": "إدخال كشف أرباح الفترة المعتمدة",
  "supersedesId": null
}
~~~

كل البنود المالية التسعة مطلوبة صراحة، حتى لو قيمتها صفر. غير سالبة، بحد مليار، ودقة حتى 6 منازل. `totalFreeOrders` مبلغ مالي، وليس عدد طلبات مجانية. أساس المثال 960 وعمولته 144.

الفترة لا تتجاوز اليوم أو نهاية الاستخدام، ولا تشمل أيامًا مثبتة. يجب أن تقع بالكامل داخل سياسة نسبة معتمدة واحدة. لا تتداخل مع كشف آخر نشط. الرد يعيد البنود ومعرف الكشف والتدقيق وأسماء العرض.

تغطية أيام النسبة المراد تثبيتها يجب أن تكون متصلة بلا فجوات. يمكن تقسيمها إلى كشوف متتابعة وتصفية كل جزء. لا يقسم النظام إجمالي كشف طويل نسبيًا على أيامه؛ تاريخ قطع التصفية يجب أن يسمح بتغطية كاملة بكشوف منتهية عند القطع.

للتصحيح قبل تثبيت الأيام، أرسل نفس الفترة مع `supersedesId` لمعرف الكشف القديم؛ يحفظ السابق ويستخدم البديل. لا تعدل مباشرة كشفًا مثبتًا.

رفع تقرير الحركات أو الطلبات اليومية لا يقوم تلقائيًا بإدخال جميع بنود كشف أرباح النسبة.

## 13. إغلاق الاستخدام العادي

`POST /handovers/{handoverId}/close`:

~~~json
{
  "effectiveAtUtc": "2026-10-10T09:00:00+03:00",
  "reason": "إنهاء استخدام حساب جاهز"
}
~~~

يغلق الإسناد ويثبت العمولة حتى يوم الإغلاق ويعيد الحساب متاحًا. لا يسدد المديونية ولا يحذف التاريخ. يمكن قبض المتبقي من الفترة المغلقة لاحقًا.

لا يمكن إغلاق فترة مغلقة، أو قبل الاستلام، أو في المستقبل، أو قبل أيام عمولة مثبتة. وجود حركات مستوردة نشطة عند لحظة الإغلاق أو بعدها يمنع الإغلاق؛ وطلبات أيام بعد يوم الإغلاق تمنعه. نقص بيانات النسبة يمنع تثبيت الإغلاق.

الإغلاق العادي لا يضبط `debtTransferred` على true؛ التصفير والتبديل المجاني يستخدمان نقل المتابعة.

## 14. استيراد تقارير جاهز

رفع ومعاينة، ثم ترحيل بعد حل المشكلات. المصدر XLSX وليس اتصال API مباشر بجاهز.

| `kind` | النوع | الورقة | الأعمدة المطلوبة |
|---|---|---|---|
| 1 | حركات مالية | `SDP_Report` | `Driver ID, Date, Delivery Price, Cash Amount, Net Amount, Driver Adjustment` |
| 2 | طلبات يومية | `Delivery Insights Report` | `Driver ID, From, To, Number Of Dispatches` |

`POST /imports` يستخدم multipart، بالحقول `kind` و`files` المتكررة؛ وللتصحيح `replacesBatchId` و`correctionReason`.

- من 1 إلى 10 ملفات، كل ملف حتى 10 MiB، والمجموع حتى 30 MiB، وعدد الصفوف حتى 50000.
- الامتداد XLSX؛ الملف نفسه لا يكرر داخل الطلب.
- الأعمدة المطلوبة يجب أن تكون موجودة، ومواضعها قد تتغير. الصيغ في الأعمدة المطلوبة تُرفض.
- يحفظ الأصل والصف والقيم المصدرية دون تقريب الدقة الأصلية.
- `Driver ID` يربط إلى رقم حساب جاهز الخارجي، ثم إلى المستخدم وقت الحركة.
- توقيت الحركة الفعلي يحدد المسؤولية، وليس اسم الملف.
- `Net Amount` السالب ينتج دينًا موجبًا بقيمة `-NetAmount`؛ الموجب ينتج رصيدًا دائنًا.
- الاستيراد لا يسجل قبضًا أو صرفًا أو صندوقًا، ولا يعيد عد التذكير.

### رد المعاينة

`batchId, kind, committed, rows, issues, files, accounts`.

- `rows`: معرف الصف، الملف، رقم الصف، رقم الحساب الخارجي، اللحظة، الحساب وفترة الاستلام والمندوب إن تم الربط، `netAmount` و`dispatches`.
- `issues`: `rowId, fileName, rowNumber, code, description`.
- `files`: `id, fileName`؛ المعرف يستخدم لتنزيل الملف.
- `accounts`: ملخص الحساب والفترة وعدد الصفوف المقروءة و`netAmount` و`platformDebtChange` وإجمالي الطلبات و`hasIssues`.
- `platformDebtChange` أثر الملف المقترح، وليس الرصيد الحالي بعد السداد.
- الصفوف التي تعذر قراءتها لا تدخل في المجاميع. الصفوف المقروءة ذات مشكلات الربط قد تظهر في الملخص مع `hasIssues`.

مشكلات المعاينة تشمل `parse_error, unknown_account, future_date, assignment_missing, multi_day_report, duplicate_daily_row, assignment_ambiguous, invalid_allocation, unknown_allocation_row, overlapping_period`.

للترحيل: `POST /imports/{batchId}/commit` بجسم `{}` للحركات. عند المشكلات يرفض الترحيل. إعادة GET للمعاينة تعيد الربط والتحقق وفق البيانات الحالية.

### الطلبات اليومية الملتبسة

التقرير يجب أن يكون ليوم واحد `From = To`. إذا تغير المستخدم أثناء اليوم، لا توزع الطلبات بالتساوي تلقائيًا؛ أرسل التوزيع اليدوي عند الترحيل:

~~~json
{
  "allocations": [
    {
      "rowId": "66666666-6666-6666-6666-666666666666",
      "handoverId": "33333333-3333-3333-3333-333333333333",
      "count": 10,
      "reason": "طلبات المستخدم الأول"
    },
    {
      "rowId": "66666666-6666-6666-6666-666666666666",
      "handoverId": "77777777-7777-7777-7777-777777777777",
      "count": 4,
      "reason": "طلبات المستخدم الثاني"
    }
  ]
}
~~~

المجموع يساوي عدد طلبات الصف، وكل فترة تخص مستخدمًا للحساب خلال اليوم، مع سبب. لا تكرر نفس فترة الاستلام في توزيعات الصف. لا تقبل نسختين نشطتين من إجمالي الحساب/اليوم نفسه. الطلبات اليومية لا تغير اليومية أو المبالغ المالية.

### التكرار والتصحيح

نفس مجموعة الملفات من النوع نفسه تعيد الدفعة الموجودة حتى لو تغير مفتاح الأمر. لا تحذف الخدمة صفوف حركات متطابقة تلقائيًا؛ قد تكون حركات صحيحة مستقلة.

تداخل نطاق توقيت الحركات مع دفعة نشطة للحساب يمنع الترحيل. للتصحيح ارفع بديلًا كاملًا للدفعة مع `replacesBatchId` وسبب. يجب الحفاظ على الحسابات وحدود الأيام، ويعكس النظام قيود الدين القديمة ويضيف الجديدة مع حفظ الأدلة. لا يستبدل جزءًا فقط، ولا يستبدل دفعة سبق استبدالها. بديل الطلبات يستبعد النسخة القديمة من التقارير.

تصحيح المصدر لا يعكس قبضًا سابقًا أو تسليم صندوق. تنزيل الأصل: `GET /import-files/{fileId}`.

## 15. الصندوق وتسليمه

| حقل رصيد الصندوق | المعنى |
|---|---|
| `fees` | إجمالي الرسوم المقبوضة غير المعتمدة كتسليم، بما فيها المحجوز |
| `settlements` | إجمالي المديونية والعمولة المقبوضتين غير المعتمدتين كتسليم |
| `reservedFees / reservedSettlements` | المقبوضات المحجوزة في طلب تسليم |
| `availableFees / availableSettlements` | المتاح لإنشاء طلب تسليم جديد |

الصندوق هنا يعرض مقبوضات وحدة جاهز؛ لا تفترض أنه مقسم بحسب المستخدم الحالي، فاستعلام الرصيد في الخدمة يجمع مقبوضات الوحدة المرخصة.

### الخطوة الأولى: إنشاء تسليم

`POST /cashbox/handovers`:

~~~json
{
  "businessDate": "2026-10-10",
  "reason": "تسليم مقبوضات جاهز للمحاسب"
}
~~~

يحجز جميع المقبوضات المتاحة المسجلة حتى نهاية اليوم، ويثبت مبلغ قسم الرسوم ومبلغ قسم التصفيات. لا يستقبل مبلغًا اختياريًا لتسليم جزء من المقبوضات. التاريخ ليس في المستقبل، ولا يقبل إذا لا يوجد مبلغ متاح.

### الخطوة الثانية: تأكيد المحاسب

`POST /cashbox/handovers/{id}/confirm`:

~~~json
{
  "feeAmount": 80,
  "settlementAmount": 52,
  "reason": "استلام ومطابقة كل قسم"
}
~~~

المحاسب مختلف عن مقدم الطلب. يجب تطابق كل قسم مستقلًا مع المبلغ المثبت، وليس المجموع فقط.

### الخطوة الثالثة: القرار النهائي

`POST /cashbox/handovers/{id}/decision` بجسم `{ "approve": true, "reason": "اعتماد التسليم" }`.

صاحب القرار مختلف عن مقدم الطلب والمحاسب. الموافقة تحتاج تأكيد المحاسب المطابق. الرفض مسموح قبل أو بعد التأكيد ويحرر الحجوزات. الطلب المعتمد لا يظهر ضمن غير المسلّم، وتبقى الأدلة والروابط.

| `status` | الحالة |
|---|---|
| 1 | معلق |
| 2 | أكد المحاسب |
| 3 | معتمد |
| 4 | مرفوض |

المقبوضات المسجلة بعد إنشاء التسليم لا تلحق به تلقائيًا، وتبقى للتسليم التالي. الحجز يمنع دخول الحركة في طلبين. تسليم الصندوق لا يخصم دين المندوب مرة أخرى ولا يحدث آخر تصفية له.

## 16. المتأخرون والإشعارات

- العد من `LastSettlementPaymentAtUtc`، أو `StartedAtUtc` إذا لا توجد تصفية.
- التأخر عند **أكثر من 10 أيام تقويمية بالرياض**؛ 10 أيام بالضبط ليست متأخرة.
- الفترة النشطة قد تكون متأخرة حتى لو الرصيد الحالي صفر؛ الفترة المغلقة تحتاج إجمالي مستحق موجب لتستمر متأخرة. هذا هو شرط `isOverdue` الحالي.
- القبض مع `countsAsSettlement: true` يعيد نقطة العد؛ رفع ملف أو طلب موافقة أو تسوية دفتر أو تصفير أو رسوم مع false لا يعيدها.
- `JahezReminderWorker` يفحص عند التشغيل ثم كل ساعة، لذلك حل الإشعار قد يتأخر حتى دورة العامل التالية.
- الإشعارات داخل النظام لأصحاب `jahez.read` ضمن جاهز، مع منع تكرار الإشعار للحلقة نفسها.
- تغيير نقطة التذكير أو زوال شرط التأخر يحل الحلقة السابقة. دين متأخر يصل لاحقًا قد يعيد فتح حلقة مغلقة.
- قائمة المتأخرين: `GET /debts?overdueOnly=true`. تشمل المستخدمين السابقين إذا بقي الدين.

## 17. الردود وأسماء العرض

الردود المالية المرتبطة بحساب أو فترة استلام تضيف بيانات عرض حسب السجل المتاح:

- `account`: `id, code, externalAccountId`.
- المالك الرسمي: `ownerRiderProfileId, ownerEmployeeId, ownerRiderNameAr, ownerRiderNameEn`.
- المستخدم الفعلي: `actualRiderProfileId, actualEmployeeId, actualRiderNameAr, actualRiderNameEn`.
- أسماء المستخدمين بجوار معرفاتهم، مثل `collectedByUserNameAr/En` و`requestedByUserNameAr/En` و`actorUserNameAr/En`، وأسماء الإنشاء والتحديث والاعتماد.
- `targetAccount` في الطلبات ذات حساب بديل.
- بعض حقول العرض قد تكون null؛ لا تفترض وجود مندوب مالك أو ترجمة إنجليزية دائمًا.

الأسماء بيانات عرض؛ المعرفات هي أساس الربط والقرارات. سجل الاستلام هو مرجع المستخدم التاريخي، وليس الإسناد الحالي للحساب.

### الحقول الأساسية للردود

| الرد | الحقول الأساسية |
|---|---|
| Handover | `id, accountId, externalAccountId, riderProfileId, assignmentId, startedAtUtc, endedAtUtc, commissionStartsOn, commissionPostedThrough, lastSettlementPaymentAtUtc, isLegacy, debtTransferred` |
| Fee | `id, handoverId, amount, waivedAmount, approvalRequestId` |
| ApprovalRequest | `id, handoverId, kind, status, requestedByUserId, targetAccountId, waiverAmount, fromDate, toDate, effectiveAtUtc, reason, externalResetReference` |
| ApprovalDecision | `id, requestId, actorUserId, status, decidedAtUtc, reason` |
| Policy | `id, handoverId, approvalRequestId, fromDate, toDate, rate` |
| Earnings | `id, handoverId, fromDate, toDate` والبنود التسعة، `supersedesId, reason` |
| Settlement | `id, handoverId, throughDate, recordedAtUtc, collectedByUserId, feePayment, debtPayment, commissionPayment, countsAsSettlement, reason` |
| LedgerEntry | `id, handoverId, bucket, kind, amount, sourceId, reversesEntryId, occurredAtUtc, reason, fromDate, throughDate, calculationJson` |
| ImportBatch | `id, kind, contentHash, uploadedByUserId, committedAtUtc, replacesBatchId, correctionReason` |
| ImportAccountSummary | `accountId, driverId, fromDate, toDate, validRowCount, netAmount, platformDebtChange, dispatches, hasIssues` |
| Dispatch | `accountId, externalAccountId, riderProfileId, handoverId, date, count` |
| CashboxEntry | `id, settlementId, handoverId, section, amount, collectedByUserId, receivedAtUtc, cashboxHandoverId` |
| CashboxHandover | `id, businessDate, status, feeAmount, settlementAmount, accountantFeeAmount, accountantSettlementAmount, requestedByUserId, accountantUserId, approvedByUserId, confirmedAtUtc, decidedAtUtc, reason, confirmationReason, decisionReason` |

سجلات History تضيف `createdAtUtc, createdByUserId`. سجلات Auditable تضيف كذلك `updatedAtUtc, updatedByUserId, rowVersion, isDeleted, deletedAtUtc, deletedByUserId, deletionReason`. وجود هذه الحقول لا يعني وجود مسار حذف/تعديل مالي مباشر.

`calculationJson` في قيد العمولة يحفظ شرائح الأيام واليومية ومراجع السياسة والموافقة وكشوف الأرباح وأساس حسابها؛ هو نص JSON يفسر عند عرض تفاصيل الحساب.

## 18. القيم الرقمية

| المجموعة | القيم |
|---|---|
| نوع الطلب `kind` | 1 إعفاء رسوم؛ 2 تبديل مجاني؛ 3 نسبة؛ 4 تصفير |
| حالة الطلب | 1 معلق؛ 2 معتمد؛ 3 مرفوض؛ 4 ملغى |
| بند الدفتر `bucket` | 1 رسوم حساب؛ 2 دين جاهز؛ 3 عمولة |
| نوع القيد `kind` | 1 استحقاق؛ 2 سداد؛ 3 تسوية؛ 4 نقل مسؤولية؛ 5 افتتاحي |
| قسم الصندوق `section` | 1 رسوم؛ 2 تصفيات |
| حالة تسليم الصندوق | 1 معلق؛ 2 أكد المحاسب؛ 3 معتمد؛ 4 مرفوض |
| نوع الاستيراد | 1 حركات؛ 2 طلبات يومية |

`kind` ليس له نفس المعنى بين طلب الموافقة وقيد الدفتر والاستيراد؛ استخدم نوع الشاشة الصحيح.

## 19. الخطأ وإعادة المحاولة وتحديث الواجهة

| HTTP | التعامل المقترح في الفرونت |
|---|---|
| 400 | عرض سبب الإدخال غير الصالح وتصحيحه |
| 401 | معالجة انتهاء/غياب المصادقة |
| 403 | لا يملك المستخدم الصلاحية أو خالف فصل المهام |
| 404 | السجل غير موجود؛ حدث القائمة |
| 409 | تعارض أو تجاوز رصيد أو فترة مثبتة أو بيانات نسبة ناقصة؛ اعرض `detail` وحدّث المصدر |
| 413 | تجاوز حد حجم طلب الرفع |

الأخطاء بصيغة ProblemDetails مع حقول مثل `title, status, detail, errorCode, correlationId`. خطأ الخدمة قد يكون `jahez.invalid_request, jahez.conflict, jahez.not_found, jahez.forbidden`؛ أخطاء ربط JSON قد تكون من API العام.

بعد انقطاع اتصال غير محسوم، أعد نفس العملية والبيانات بالمفتاح نفسه. عند تعديل البيانات أنشئ مفتاحًا جديدًا. لا تعتبر 409 نجاحًا ولا تنشئ تلقائيًا عملية قبض بديلة.

| العملية الناجحة | ما يجب إعادة جلبه |
|---|---|
| الاستلام/الإغلاق/التبديل/التصفير | الحسابات والإسنادات وفترات الاستلام والأرصدة |
| التصفية | الرصيد والدفعات والدفتر والصندوق |
| إعفاء الرسوم | الطلب وقراره والرسوم والرصيد والدفتر |
| اعتماد النسبة | الطلب والسياسات والرصيد ومشكلات اكتمال الأرباح |
| إدخال/تصحيح الأرباح | الأرباح والرصيد |
| التسوية المباشرة | الرصيد والدفتر |
| ترحيل/استبدال ملف | المعاينة والرصيد والدفتر أو تقرير الطلبات حسب النوع |
| إنشاء/تأكيد/قرار تسليم الصندوق | رصيد الصندوق وتسليماته وحركاته |

## 20. مراجعة صفحات الفرونت المقترحة

هذه نقاط قبول ومراجعة، وليست نتائج اختبار تم تنفيذها على الفرونت:

- [ ] اختيار المندوب الفعلي مستقل عن صاحب الحساب الرسمي.
- [ ] اختيار `handoverId` الصحيح، وليس `accountId` مكانه.
- [ ] كفيل الحساب `sponsorId` واحد؛ لا حقل داشبورد مستقل.
- [ ] استلام جاهز وإغلاقه من مسارات جاهز فقط.
- [ ] العمولة المستحقة تُقرأ من الـBackend، ومبلغ تحصيلها يمثل المقبوض.
- [ ] مجموع العمولة المعروضة يشمل المثبتة وغير المثبتة.
- [ ] الرسوم لا يعاد فرضها كل تصفية.
- [ ] السداد الجزئي يبقي الباقي مستحقًا، ولا يظهر كإعفاء.
- [ ] true إلزامية عند قبض مديونية أو عمولة.
- [ ] التاريخ المختار قطع للفترة، وليس إدخالًا لوقت القبض.
- [ ] نقص أرباح النسبة ظاهر للمستخدم قبل التصفية.
- [ ] الطلب المعلق لا يظهر كسياسة معتمدة أو تخفيض نافذ.
- [ ] اعتماد/رفض الطلب مخفي عن مقدمه، مع صلاحية النوع الصحيحة.
- [ ] طلب 15% يحتاج من/إلى، دون حقل مبلغ تخفيض أو نسبة قابلة للتغيير.
- [ ] «إعفاء رسوم» لا يسمى «إعفاء عمولة» في النص أو العرض.
- [ ] «تصفير الحساب» لا يوحي بأن دين المندوب سيختفي.
- [ ] التسوية المباشرة لا تقدم كطلب ينتظر اعتمادًا.
- [ ] الصندوق يفصل الرسوم عن التصفيات، وتأكيده يطابق القسمين.
- [ ] الأدوار الثلاثة لتسليم الصندوق مختلفة.
- [ ] المعاينة والاستيراد لا يظهران كمبالغ مقبوضة.
- [ ] تقرير الطلبات متعدد الأيام لا يوزع يوميًا تلقائيًا.
- [ ] مشكلات الاستيراد والتوزيع اليدوي والتصحيح الكامل ظاهرة.
- [ ] مفاتيح عدم التكرار محفوظة خلال إعادة المحاولة.
- [ ] الفرونت يستخدم صلاحيات المسارات الحالية، لا أسماء manage القديمة.
- [ ] لا أزرار تعديل/حذف قبض أو سجل مالي دون Endpoint فعلي.

### سيناريوهات مراجعة عملية

| السيناريو | النتيجة المتوقع مراجعتها |
|---|---|
| رسوم 0، دين 42، عمولة 30؛ سداد عمولة 10 فقط | عمولة متبقية 20، الدين يبقى 42، صندوق التصفيات +10 |
| نفس الدفعة تتكرر بنفس المفتاح والجسم | لا قبض أو صندوق إضافي |
| نفس المفتاح مع تغيير المبلغ | 409 |
| سداد عمولة مع false | رفض |
| رسوم فقط مع false | قبول ضمن المستحق، دون إعادة عد التذكير |
| طلب نوع 1 بمبلغ 10 | عند الاعتماد يخفض الرسوم فقط |
| طلب نوع 3 دون تواريخ | رفض |
| طلب نوع 3 مع فترة عمولة مثبتة | الاعتماد يُرفض |
| اعتماد نسبة بلا أرباح مكتملة | المعاينة توضح النقص وتثبيت التصفية يُرفض |
| اليومية 10 أيام، أساس نسبة 500 | اليومية 150 مقابل نسبة 75 عند اكتمال البيانات |
| مبلغ سالب في تسوية بند العمولة | قيد يخفض العمولة، لا قبض ولا طلب موافقة |
| المستخدم يعتمد طلبه | رفض |
| تصفير مع دين باق | الحساب يتاح، والدين يبقى على السابق |
| تسليم صندوق بمجموع صحيح وتوزيع خاطئ | رفض تأكيد المحاسب |
| قبض جديد بعد حجز الصندوق | يبقى متاحًا للتسليم التالي |
| 10 أيام دون تصفية، ثم 11 | التأخر يبدأ عند 11 يومًا وفق شرط أيام الرياض |

## 21. مسارات الحسابات والمراجع المساندة

إنشاء وإدارة حسابات المنصة خارج `JahezController`. للمراجعة استخدم المسارات الموجودة في المشروع مثل `/api/platform-accounts` و`/api/platform-operations/accounts`، والمنصات `/api/platforms`، والكفلاء `/api/sponsors`، والمدن `/api/hr-catalogs/operating-cities` والمندوبين `/api/riders`.

عقد حساب المنصة له تمثيلات مختلفة بين الواجهة الأساسية والتوافق؛ لا تنقل الحقول بينهما تلقائيًا. أمثلة وعقود الحسابات الكاملة في دليل التسليم المشار إليه أدناه، مع ملاحظة أن صلاحياته وبعض عباراته أقدم من الكود الحالي. قائمة Endpoints جاهز في القسم 4 هي مرجع هذه المراجعة.

الإشعارات من نظام الإشعارات الحالي، مثل `/api/notifications`، بصلاحيات الإشعارات إضافة إلى شروط عرض جاهز. لا توجد رسائل خارجية أو أتمتة Codex ضمن الخدمة.

تمت هذه المراجعة بقراءة الملفات الحالية ومقارنتها، دون تنفيذ اختبارات تشغيل أو طلبات API أو التحقق من نشر الإنتاج. اختبارات المشروع الموجودة ليست دليلًا على نجاح الفرونت الحالي ما لم تُشغل عليه السيناريوهات وتُراجع طلباته.

**المطلوب من مبرمج الفرونت في نقطة التخفيض:** تقديم اسم العملية المقصودة، والـEndpoint الفعلي، وJSON المرسل، ونتيجة الاعتماد في الرصيد والدفتر. بعدها يمكن تحديد هل الشاشة مطابقة لإعفاء الرسوم أو النسبة، أم تعرض وظيفة تخفيض بموافقة لم ينفذها الـBackend.
