## Procedure

Tool: `tools/Apply-HungerV21Migrations.ps1` with scripts `database/scripts/hunger-v21-application.sql` and `hunger-v21-identity.sql` (generated by `dotnet ef migrations script` from the hosted baseline).

1. Checked the hosted baseline was `20261104115133_…` / `20261104115200_…` and that none of the new migrations were present.
2. Rehearsal: all 62 batches ran inside one serializable transaction and were rolled back.
3. `BACKUP DATABASE … WITH COPY_ONLY, CHECKSUM` → `D:\Services\MSSQL\Backup\db67927_before_hunger_v21_20261106_163620.bak` (restore not verified — no CREATE DATABASE right, same as the 4 Nov deploy).
4. Applied all batches in one transaction and committed.
5. Fresh connection confirmed all 8 migration IDs; re-running the tool reports "already present".

## Data impact

Before applying, hosted `hunger.FinancialEvents`, `SettlementDocuments`, `WalletReviews`, `AlertRules` and `DailyOperations` were all empty, so the data-conversion statements (withdrawals → Arrived, adjustments → Unmatched, remittance status derivation, review status) changed no rows. Every new required column has a default, so the currently deployed API keeps working against the new schema.

Hosted now has 12 tables in `hunger` and 24 permission definitions (`hunger.*` + `fleet.vehicles.fields.identity`), matching `PermissionKeys` exactly.
