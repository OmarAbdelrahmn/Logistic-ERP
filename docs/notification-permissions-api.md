# Permission-filtered notification API

The client supplies the permission groups it wants in the feed. The server intersects those keys with the authenticated user's current permissions, then filters that user's notifications **before pagination and counting**. Client-supplied keys do not grant access.

## Request and response

`POST /api/notifications/query`

Requires the authenticated user's bearer token and `notifications.read`.

```json
{
  "permissions": [
    "fleet.accidents.read",
    "fleet.vehicles.read",
    "platform_assignments.read"
  ],
  "unreadOnly": false,
  "pageSize": 50,
  "cursor": null
}
```

The response contains:

```json
{
  "items": [],
  "nextCursor": null,
  "unreadCount": 0,
  "effectivePermissions": ["fleet.vehicles.read"]
}
```

This example means the user actually holds only `fleet.vehicles.read` from the requested list and currently has no matching notifications. Actual items include the existing notification fields and an additional `permissionKeys` array describing their audience.

- Matching uses **any** granted/requested audience permission, not all of them.
- Permission keys match exactly. Unknown keys return validation errors. Known keys the user does not hold are excluded from `effectivePermissions`.
- An explicit empty array returns an empty feed and zero unread count.
- Omitting `permissions`, or sending `null`, uses all current server-authorized permissions and also includes personal notifications that have no permission audience.
- An explicit permission filter excludes untagged personal notifications because they do not belong to a requested permission group.
- `unreadCount` covers all currently visible unread notifications matching the same permission filter; it is independent of the page and cursor.
- `pageSize` is 1–200. Send the returned opaque `nextCursor` with the **same filter** for subsequent pages.
- The authenticated user determines ownership. The request does not accept another user's ID or a role name.
- Revoked permissions hide matching notifications from the feed and count, and prevent changing their state. They remain stored in history.
- Notifications are delivered to eligible recipients when the event occurs. This API does not retrospectively deliver every historical event to users granted a permission later.

## Existing GET endpoints

The existing responses remain compatible. Repeat the query parameter for multiple keys:

```text
GET /api/notifications?permissions=fleet.accidents.read&permissions=fleet.vehicles.read&unreadOnly=false&pageSize=50
GET /api/notifications/unread-count?permissions=fleet.vehicles.read
```

Without a `permissions` query parameter, both endpoints derive the user's current permissions on the server.

## Read state and history

```text
POST /api/notifications/{id}/state
```

```json
{ "action": "read", "rowVersion": "<notification-rowVersion>" }
```

Reading preserves the notification. Use `unreadOnly: false` to include previously read notifications. Other existing actions are `unread`, `acknowledge`, and `archive`. A user can change only their own notifications that they are currently permitted to access.

## Permission audiences

| Producer | Any matching permission |
| --- | --- |
| Accidents and claim deadlines | `fleet.accidents.read`, `fleet.vehicles.read`, `platform_assignments.read`, `maintenance.work_orders.read` |
| Vehicle compliance/expiry | `fleet.compliance.read` |
| Employee document compliance/expiry | `employees.read` |

Notifications generated by these services carry the audience automatically. Accident delivery also checks these permissions before creating each recipient's notification. Responses and counts recheck current permissions, so the client cannot broaden access with a forged permission list.

An authorized notification creator using `POST /api/notifications` can supply `permissionKeys` to associate another notification with a permission audience. All keys must be known; an empty audience is rejected. Omission creates a personal notification. The ordinary creation endpoint still requires `notifications.manage`.
